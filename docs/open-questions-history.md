2. `UNKNOWN_logic_hz` — **MOSTLY CLOSED `[STATIC]` + `[PROVEN]` rate consistency, 2026-10-10: 16.72 Hz = 1193182 / 0x5CEC / 3.** The game reprograms PIT channel 0 to divisor 0x5CEC (`1000:2047`), its timer ISR (`1000:2092`) decrements `cs:[2085]`, the loop sets it to 3 every iteration (`1000:010B`) and the pel-pan routine waits for it to reach 0 (`1000:1605`); all four sites are asserted from the file bytes in `npm run verify`. The measured 16.9 +/- 0.4 calls/s agrees. The retrace wait of call 14 could add up to one retrace period; whether it does in practice (rate between about 13.5 and 16.72 Hz) is not separated by the one measurement, so re-measure at another cycles setting to close it fully. ⚠️ The earlier text below (a 4-vsyncs-per-iteration hypothesis, 17.5 Hz) is superseded.
   Original entry: **OPEN.** `docs/port-plan.md` concludes the main loop is paced by vsync and the ~50.15 Hz timer ISR drives sound, so the port uses `requestAnimationFrame`. That was not traced against the real frame counter. gods-web's equivalent turned out to be an exact 15 Hz derived from the PIT divisor and a wait on a counter. `[UNKNOWN]` for the real logic rate — read `Video_WaitVsyncAndCountFrame`'s wait condition and measure live.
   **Partial measurement, 2026-10-09 (`[PROVEN]` live, one run, one cycles setting):**
   - `Video_WaitVsyncAndCountFrame` (`CS:0x142`, live CS `0x1F5`) waits for the 3DA retrace bit to go set then clear and does `add word [89F6],1` at `CS:0x151`: exactly one vsync per call, no multi-vsync wait inside it. It is also used by a menu timed-delay helper at `CS:0x10B` (`mov [89F6],0` / call / `cmp [89F6],0`), so `[89F6]` is cleared by callers and reads 0 at rest.
   - In real gameplay (world 1, level start), 67 calls of that `add` took 72 BIOS ticks at `0040:006C` (18.2065 Hz), i.e. **about 16.9 calls per emulated second (±~0.4)**, in DOSBox 0.84 with this bridge's default cycles. That is neither a 70 Hz vsync lock nor 15 Hz.
   - Hypotheses, NOT distinguished yet: (a) the loop effectively takes 4 vsyncs per iteration (70.086 / 4 = 17.5 Hz, within error), or (b) the loop is CPU-bound under DOSBox's cycles setting. Re-measure at a different cycles setting to tell them apart.
   - **Main-loop shape `[STATIC]`, read live from the demo starter's copy of the loop (`CS:0x55`–`0x7A`)**: `mov [89F6],0` / `mov cs:[2085],3`, then 14 calls in the documented order (`2171, 21F3, 92F5, 349A, 2F78, E1DF, 20A9 = Demo_PlaybackInput, E86D, 2129 = Demo_RecordInput, 27DD, 37F4 = Input_ReadState, 2AE2, 314C, 2092 = vsync wait`), then `jmp` back. So **one loop iteration = one logic tick**, and the only pacing is one retrace wait per iteration (the unexplained `cs:[2085]=3` is not yet traced). An iteration that takes longer than a retrace period waits for the next retrace, so the real rate is 70.086 Hz divided by a whole number, which fits 16.9 Hz (a mix of 4- and 5-period iterations) better than a fixed 17.5 or 15. Consequence for the port: replay and parity must be indexed by iteration, never by wall-clock time; any fixed Hz in the port is a display choice, not a recovered constant.
   - Method note: DOSBox's `dosbox_status.frame` keeps advancing while the debugger is paused, so it must not be used to time anything. Use the BIOS tick dword plus a breakpoint `hit_count` read while paused.

5. `UNKNOWN_frame_source_mode_0` — **RESOLVED (2026-10-10).** The pointer tables are tile *streams*, one byte per cell, column-major: `bx = DS word [table + 2*frame]` where `table` is `0xE4FA` (default, class 5, type 0x2b), `0xE906` (class 2/4, and type 8 in mode 0xf) or `0xDEA2` (type 0x2d); descriptor (`DS:0xC39A + 2*type`) `+0xa` columns, `+0xc` rows, `+0xe` bank, `+0x12/+0x14` cell width/height, `+0x16` frameSourceMode (0 = stream byte is the tile index, 1 = the entity frame `+0xa` itself, other = video memory). The cell blitters are chosen by the entity's `+0x16` draw mode: `0xe` 16x16 tiles (160 bytes), `0xf` 32x32 (640), `0xa` 32x16 half tiles (byte = tile*2+half, 0 = empty), `0xd` one 32x32 tile drawn bottom-up. Facing flips use a pre-mirrored copy of the bank (1000:B449). Implemented in `web/render/sprites.js`; `[STATIC]` for the disassembly reading, `[PROVEN]` for: bank layout (tile 9 of banks 2/3/6/7 and the mirrored banks 8 and 2' read live from DOSBox equal the depacked pak bytes / `mirrorTile32`), and two live frames (player facing right and left, `[8B69]`=0x1C) reproduced 2681 of 2764 sprite pixels exactly (remaining 83 = score digits the HUD pass draws). Still `[UNKNOWN]`: the `[8C38]` second-layer overlay (772C), the 0xffff video-memory grab, mode `0xb` internals, and the stream bytes the HUD rewrites in DS (the port relies on the engine's own writes).
