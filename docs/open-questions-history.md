## Open questions — ranked

1. ~~`UNKNOWN_autoplay_format`~~ — **CLOSED `[STATIC]` for the format, 2026-10-09**, see `docs/formats/pin.md` and `web/core/demo-tape.js`. Live disassembly of `Demo_PlaybackInput` (`CS:0x159`), `Demo_RecordInput` (`CS:0x1D9`) and the demo starter (`CS:0x89`, `Game_StartAttractDemoAndRunLoop`) shows `data/autoplay.pin` is the attract-demo tape: `(count, state)` byte pairs, terminated by the word `0xFFFF` (byte 628), 314 records, 2342 loop iterations; loaded at `DS:0x8200` with `[8BA6]` pointing at the first record. Each iteration overwrites both input bytes `[8B67]`/`[8B68]` with the current state and decrements the count byte `[8BA8]`; a record of count N applies on exactly N iterations. The starter also sets world word `[8B89]=0`, sublevel `[8B8B]=1`, RNG state `[8B71]=0x3141`, score `[8B75]=0` and the playback flag `[8BAA]=1`. State bits: Up `0x01`, Down `0x02`, Left `0x04`, Right `0x08`, Fire `0x80` (`[PROVEN]` live; the table is built at startup from `pockets.ini`, not stored in the EXE). ⚠️ An earlier version of this entry read the terminator as `00 00` and the state bits as an unmatched 5-bit mask; both were wrong. Still open: running the demo live and confirming the cursor walks the whole tape and which level it plays (`UNKNOWN_demo_which_level`).
2. `UNKNOWN_logic_hz` — **OPEN.** `docs/port-plan.md` concludes the main loop is paced by vsync and the ~50.15 Hz timer ISR drives sound, so the port uses `requestAnimationFrame`. That was not traced against the real frame counter. gods-web's equivalent turned out to be an exact 15 Hz derived from the PIT divisor and a wait on a counter. `[UNKNOWN]` for the real logic rate — read `Video_WaitVsyncAndCountFrame`'s wait condition and measure live.
   **Partial measurement, 2026-10-09 (`[PROVEN]` live, one run, one cycles setting):**
   - `Video_WaitVsyncAndCountFrame` (`CS:0x142`, live CS `0x1F5`) waits for the 3DA retrace bit to go set then clear and does `add word [89F6],1` at `CS:0x151`: exactly one vsync per call, no multi-vsync wait inside it. It is also used by a menu timed-delay helper at `CS:0x10B` (`mov [89F6],0` / call / `cmp [89F6],0`), so `[89F6]` is cleared by callers and reads 0 at rest.
   - In real gameplay (world 1, level start), 67 calls of that `add` took 72 BIOS ticks at `0040:006C` (18.2065 Hz), i.e. **about 16.9 calls per emulated second (±~0.4)**, in DOSBox 0.84 with this bridge's default cycles. That is neither a 70 Hz vsync lock nor 15 Hz.
   - Hypotheses, NOT distinguished yet: (a) the loop effectively takes 4 vsyncs per iteration (70.086 / 4 = 17.5 Hz, within error), or (b) the loop is CPU-bound under DOSBox's cycles setting. Re-measure at a different cycles setting to tell them apart.
   - **Main-loop shape `[STATIC]`, read live from the demo starter's copy of the loop (`CS:0x55`–`0x7A`)**: `mov [89F6],0` / `mov cs:[2085],3`, then 14 calls in the documented order (`2171, 21F3, 92F5, 349A, 2F78, E1DF, 20A9 = Demo_PlaybackInput, E86D, 2129 = Demo_RecordInput, 27DD, 37F4 = Input_ReadState, 2AE2, 314C, 2092 = vsync wait`), then `jmp` back. So **one loop iteration = one logic tick**, and the only pacing is one retrace wait per iteration (the unexplained `cs:[2085]=3` is not yet traced). An iteration that takes longer than a retrace period waits for the next retrace, so the real rate is 70.086 Hz divided by a whole number, which fits 16.9 Hz (a mix of 4- and 5-period iterations) better than a fixed 17.5 or 15. Consequence for the port: replay and parity must be indexed by iteration, never by wall-clock time; any fixed Hz in the port is a display choice, not a recovered constant.
   - Method note: DOSBox's `dosbox_status.frame` keeps advancing while the debugger is paused, so it must not be used to time anything. Use the BIOS tick dword plus a breakpoint `hit_count` read while paused.

4. `UNKNOWN_level_spawn_positions` — **OPEN.** Real per-level start positions come from a per-sublevel "camera position" table at `6de3:0000` that is all zero in the static image and populated through a computed pointer (no Ghidra xrefs). 9. `UNKNOWN_alt_ground_table_extent` — **OPEN, opened by the first verify run.** `docs/engine.md` says a second, stricter table sits at `6de3:f27b` ("near-identical, every 16 replaced by 0").
