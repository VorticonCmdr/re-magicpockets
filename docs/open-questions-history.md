## Open questions — ranked

1. ~~`UNKNOWN_autoplay_format`~~ — **CLOSED `[STATIC]` for the format, 2026-10-09**, see `docs/formats/pin.md` and `web/core/demo-tape.js`. Live disassembly of `Demo_PlaybackInput` (`CS:0x159`), `Demo_RecordInput` (`CS:0x1D9`) and the demo starter (`CS:0x89`, `Game_StartAttractDemoAndRunLoop`) shows `data/autoplay.pin` is the attract-demo tape: `(count, state)` byte pairs, terminated by the word `0xFFFF` (byte 628), 314 records, 2342 loop iterations; loaded at `DS:0x8200` with `[8BA6]` pointing at the first record. Each iteration overwrites both input bytes `[8B67]`/`[8B68]` with the current state and decrements the count byte `[8BA8]`; a record of count N applies on exactly N iterations. The starter also sets world word `[8B89]=0`, sublevel `[8B8B]=1`, RNG state `[8B71]=0x3141`, score `[8B75]=0` and the playback flag `[8BAA]=1`. State bits: Up `0x01`, Down `0x02`, Left `0x04`, Right `0x08`, Fire `0x80` (`[PROVEN]` live; the table is built at startup from `pockets.ini`, not stored in the EXE). ⚠️ An earlier version of this entry read the terminator as `00 00` and the state bits as an unmatched 5-bit mask; both were wrong. Still open: running the demo live and confirming the cursor walks the whole tape and which level it plays (`UNKNOWN_demo_which_level`).
2. `UNKNOWN_logic_hz` — **OPEN.** `docs/port-plan.md` concludes the main loop is paced by vsync and the ~50.15 Hz timer ISR drives sound, so the port uses `requestAnimationFrame`. That was not traced against the real frame counter. gods-web's equivalent turned out to be an exact 15 Hz derived from the PIT divisor and a wait on a counter. `[UNKNOWN]` for the real logic rate — read `Video_WaitVsyncAndCountFrame`'s wait condition and measure live.
   **Partial measurement, 2026-10-09 (`[PROVEN]` live, one run, one cycles setting):**
   - `Video_WaitVsyncAndCountFrame` (`CS:0x142`, live CS `0x1F5`) waits for the 3DA retrace bit to go set then clear and does `add word [89F6],1` at `CS:0x151`: exactly one vsync per call, no multi-vsync wait inside it. It is also used by a menu timed-delay helper at `CS:0x10B` (`mov [89F6],0` / call / `cmp [89F6],0`), so `[89F6]` is cleared by callers and reads 0 at rest.
   - In real gameplay (world 1, level start), 67 calls of that `add` took 72 BIOS ticks at `0040:006C` (18.2065 Hz), i.e. **about 16.9 calls per emulated second (±~0.4)**, in DOSBox 0.84 with this bridge's default cycles. That is neither a 70 Hz vsync lock nor 15 Hz.
   - Hypotheses, NOT distinguished yet: (a) the loop effectively takes 4 vsyncs per iteration (70.086 / 4 = 17.5 Hz, within error), or (b) the loop is CPU-bound under DOSBox's cycles setting. Re-measure at a different cycles setting to tell them apart.
   - **Main-loop shape `[STATIC]`, read live from the demo starter's copy of the loop (`CS:0x55`–`0x7A`)**: `mov [89F6],0` / `mov cs:[2085],3`, then 14 calls in the documented order (`2171, 21F3, 92F5, 349A, 2F78, E1DF, 20A9 = Demo_PlaybackInput, E86D, 2129 = Demo_RecordInput, 27DD, 37F4 = Input_ReadState, 2AE2, 314C, 2092 = vsync wait`), then `jmp` back. So **one loop iteration = one logic tick**, and the only pacing is one retrace wait per iteration (the unexplained `cs:[2085]=3` is not yet traced). An iteration that takes longer than a retrace period waits for the next retrace, so the real rate is 70.086 Hz divided by a whole number, which fits 16.9 Hz (a mix of 4- and 5-period iterations) better than a fixed 17.5 or 15. Consequence for the port: replay and parity must be indexed by iteration, never by wall-clock time; any fixed Hz in the port is a display choice, not a recovered constant.
   - Method note: DOSBox's `dosbox_status.frame` keeps advancing while the debugger is paused, so it must not be used to time anything. Use the BIOS tick dword plus a breakpoint `hit_count` read while paused.
3. ~~`UNKNOWN_player_entity_slot`~~ — **CLOSED `[PROVEN]`, 2026-10-09** by the full attract-demo capture (2341 iterations, `tools/attract-capture/autoplay.capture.json`). Entity slot 1 (`DS:0x9092` pointer, record at `0x93DA`, kind 3) is a **constant screen-space marker**: its `+6/+8` read (144, 80) on all 2341 rows. It is the player's on-screen anchor, which is why an earlier live read saw it frozen. Slot 0 (record at `0x9398`) carries the **scroll origin** (the negated world position, shifted by the screen anchor) and is what input moves: Right (`0x08`) gives dx -4 per iteration, Left (`0x04`) dx +4, jumps/falls change dy; its values equal the camera globals `[8BBB]/[8BBD]` on every row but one (iteration 1459). Over the demo the origin spans x -3748..-80, y -1072..-512. ⚠️ Earlier prose in `docs/port-plan.md` that treated slot 1 as "the player's position" is wrong; the player's world position is derived from slot 0.

13. ~~`UNKNOWN_rng_carry_in`~~ — **CLOSED `[PROVEN]` for call #13, 2026-10-09**; one residual open. Against a live DOSBox capture of the whole attract demo (`tools/attract-capture/autoplay.capture.json`, 2341 consecutive iterations), `web/engine/rng.js` reproduces 2191 of 2340 transitions as exactly one step. Two things were wrong in the earlier port and are fixed: (1) every x86 `xor` clears CF, so each `rcr` after an `xor` starts with carry 0 (the old file chained the carry through the `xor`s and matched nothing); (2) the carry the first `rcr` (`1000:1207`) consumes is **1** at the main loop's call #13, on every single-step transition, never 0. ⚠️ The earlier text here and in `rng.js` said carry-in was unknowable without tracking CPU flags and assumed 0; both wrong. Residual `UNKNOWN_rng_extra_caller` is **explained `[STATIC]`, 2026-10-09**: `Entity_RollRandomBehaviorIndex` (`1000:71D5`) calls the generator with the carry left by a preceding `cmp byte [8BA3],0` (CF = 0), and the enemy AI calls it several times per iteration (kind-2 think functions, AI opcodes, the class switch), which is where the 149 multi-step transitions (clustered in iterations ~1000-1400, where enemies are active) come from; it is ported in `web/engine/enemy.js` (`rollRandom`, carry 0). The conformance counts do not yet depend on it: iterations with several rolls are not among the first 700. The demo's seed is `0x3141`, set by the demo starter.

19. ~~`UNKNOWN_player_motion_rules`~~ — **CLOSED `[PROVEN]` for the demo's first 700 iterations, 2026-10-09**, by one-step conformance (`npm run verify`, `tools/attract-capture/conformance.mjs`): the ported iteration reproduces entities 0-2 byte for byte on 694 of 699 captured transitions and every non-scratch global on 595. The mechanism, as ported: input byte `[8B67]` (bits Up 1, Down 2, Left 4, Right 8, Fire 0x80) is masked by `~(flags | [8B5E])` and read by `Entity_HandleCollisionOrStateDispatch` (`1000:3CE8`), called from the world entity (class 1). Left/Right add `-/+[8B97]` (4) to the WORLD entity's X through `1000:D596` when the player's state is 0, 0x1D, 0x11, 0x35, 0x5B or 0x5D (that is why the hero only walks in states 0 and 29); Up starts a jump (world state 0x10, player state 0x12); falling and jumping are scripts on the world entity (`op 55` = `1000:DD1A`, speed -2 per iteration down to -13, and `op 9` arcs); the player's terrain flags come from `E067`/`E14F` four tile scans against the per-world table, which choose between falling (`F77B`), landing/bounce (`F489`, `F619`) and lateral blocking (`F842`, `F960`); `Camera_UpdateScroll` (`0221`) splits the world position into tile and pixel parts after each update. Not ported (the five transitions that still differ): the intro `opcode 68` sequence, `F77B` with the player in state 0x1D, enemy hits (`45F8`), weapon variant 14, and `5609` (the charge-meter maximum). Other entities (enemy kinds 2, 4, 5, 6, 7, entity freeing, the event queue consumer) are not ported.
